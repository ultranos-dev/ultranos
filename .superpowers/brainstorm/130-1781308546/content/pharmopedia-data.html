Data layer

SQLite schema, FTS5 search index, sync orchestration

SQLite tables (src/db/schema.ts)
drug_catalog
atc_code TEXT PRIMARY KEY
inn_name TEXT NOT NULL
brand_names TEXT -- JSON array
dose_forms TEXT -- JSON array
therapeutic_class TEXT
local_names TEXT -- JSON object {en, prs, ps}
tier1_json TEXT -- full Tier1 payload as JSON
tier2_json TEXT -- full Tier2 payload as JSON (null for patients)
tier3_json TEXT -- full Tier3 payload as JSON (null for non-pharmacist)
version INTEGER NOT NULL
drug_catalog_fts (FTS5 virtual table)
content='drug_catalog', content_rowid='rowid'
Indexed: inn_name, atc_code, brand_names_flat, local_names_flat
brand_names_flat / local_names_flat = JSON arrays joined to space-separated string
sync_meta
key TEXT PRIMARY KEY -- e.g. 'lastVersion', 'lastSyncAt'
value TEXT NOT NULL
Sync flow (src/sync/catalog-sync.ts)
1 App foregrounds → check network
2 Read lastVersion from sync_meta (0 if first run)
3 Call drugCatalog.sync(sinceVersion, limit: 200)
4 Upsert rows into drug_catalog + rebuild FTS triggers
5 Save new latestVersion to sync_meta
6 Repeat until entries.length === 0
Sync state (status: 'idle' | 'syncing' | 'error', lastSyncAt) held in zustand sync-store.
First-run: blocking splash progress bar. Subsequent: background, non-blocking.
Tier payload storage strategy
Each row stores the full tier-scoped payload the API returned at sync time. The app never re-scopes locally — it trusts what the server sent. Tier 2+ fields only populated if the user's role grants them (server enforces this on sync). If a user's role changes, a fresh sync overwrites rows with the new tier payload.
