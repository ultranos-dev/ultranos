Architecture approaches

Three ways to structure the Pharmopedia standalone app

A

expo-router + expo-sqlite (FTS5) + zustand

Navigation: Expo Router file-based routing — screens are files, deep links are free, URL-like navigation.

Offline DB: expo-sqlite with an FTS5 virtual table for full-text search. Manual schema, full control.

State: Zustand slices for sync state (lastVersion, syncStatus) and UI state.

Pros

  • Modern Expo standard (Expo recommends expo-router)
  • Deep linking + web support built-in
  • FTS5 gives fast offline search

Cons

  • Different nav approach than Patient Lite Mobile (react-navigation)

⭐ Recommended

B

react-navigation + expo-sqlite (FTS5) + zustand

Navigation: React Navigation — same library used in Patient Lite Mobile. Stack + Tab navigators.

Offline DB: Same expo-sqlite + FTS5 approach as A.

State: Same zustand approach as A.

Pros

  • Exact same navigation patterns as Patient Lite Mobile
  • Familiar to anyone who worked on that app

Cons

  • react-navigation is being superseded by expo-router for new apps
  • More boilerplate (navigator definitions, type files)
C

expo-router + WatermelonDB + zustand

Navigation: Expo Router (same as A).

Offline DB: WatermelonDB — reactive observable queries, built on SQLite, purpose-built for sync-heavy mobile apps.

State: WatermelonDB handles most observable state; zustand for UI only.

Pros

  • Reactive queries — UI auto-updates when DB changes
  • Designed for offline-first sync patterns

Cons

  • Significant complexity overhead for a read-heavy catalog
  • Custom sync adapter to write against our Hub API sync endpoint
  • Heavier bundle
