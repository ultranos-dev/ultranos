# Story 59.2: Hub Contract CI Guard & Typed Spoke Clients

Status: ready-for-dev

## Story

As a platform engineer,
I want a CI-enforced contract between every spoke's Hub calls and the Hub's actual router surface — plus compile-time-typed clients for the three raw-fetch spokes,
so that client↔hub drift (which has silently killed at least 14 features to date) becomes a build failure instead of a runtime mystery.

## Acceptance Criteria

1. **Given** any spoke source tree, **when** the contract test runs in CI, **then** every `/router.procedure` path the spoke calls is verified to exist in the Hub's `_app.ts` router map — a nonexistent procedure fails the build with the offending file:line.
2. **Given** the Hub removes or renames a procedure that any spoke calls, **then** the same test fails — the contract is bidirectionally protective.
3. **Given** the three raw-fetch spokes (opd-lite, lab-lite, pharmacy-lite), **when** they call the Hub, **then** calls go through a shared thin client that is TYPED against the Hub's `AppRouter` via type-only imports (no runtime dependency on hub-api), covering at minimum all procedures used today; admin-portal's existing typed tRPC client is the reference.
4. **Given** wire-shape asymmetries (e.g., `sync.push` conflict responses return HLC as an object while requests carry serialized strings — `sync.ts:12-18` vs `:180-197`), **then** the shared types capture both shapes explicitly so clients can't mis-assume.
5. **Given** a new spoke call is added without registering in the contract inventory, **then** CI fails (the inventory is generated by grep/AST scan, not hand-maintained, wherever feasible).
6. **Zero regression:** zero behavior change at runtime — this story is type/CI infrastructure plus mechanical call-site migration to the shared client; all pre-existing tests pass; `pnpm typecheck` passes; no feature or functionality is removed or degraded.

## Dev Notes

### Audit Findings Addressed

- **C-SYS-5 (structural half)** and audit §10 Theme 1: "One CI contract test kills this class." **M-LAB-10 [A]**: stringly-typed client with two self-documented historical drift incidents plus the live ones. **Type-mismatch risks** (audit §9): per-spoke DTO re-declarations, HLC wire asymmetry, `hlcTimestamp` accepted as any string.

### Architecture

- Type-only import from hub-api inside a pnpm workspace is safe (no runtime coupling) — the audit and admin-portal precedent support it. If hub-api's build makes type-only import awkward, generate a `.d.ts` router snapshot as a build artifact instead.
- Sequencing: land Task 1 (guard) FIRST — it protects Story 59.1's repairs immediately; Task 2 (client migration) can follow in the same story or be split per-spoke across PRs.
- Do NOT change payloads/semantics during migration — behavior-preserving refactor only. Anything found broken during migration gets logged against its owning story, not fixed inline.

### Zero-Regression Mandate

This story must introduce **zero regression in existing features and functionality**. It is infrastructure + mechanical migration: every request leaving a spoke is byte-equivalent (headers/body/path) to before, verified by fixture comparison on the top flows. All pre-existing tests pass; `pnpm typecheck` clean.

### Project Structure Notes

**New files:** `packages/hub-client/` (or per-app client modules), `scripts/extract-hub-calls.ts`, `apps/hub-api/src/__tests__/spoke-contract.test.ts`, CI workflow update.
**Files to modify:** three spokes' `lib/trpc.ts` call sites (mechanical).
