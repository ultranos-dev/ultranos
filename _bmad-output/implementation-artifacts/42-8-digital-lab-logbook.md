# Story 42.8: Digital Lab Logbook

Status: pending

## Story

As a lab manager,
I want an auto-populated digital logbook that replaces the legally required paper register,
so that the logbook is always current, searchable, backed up, and ready for inspection.

## Acceptance Criteria

1. **Given** a result has been authorized and released, **when** the system appends it to the digital logbook, **then** the logbook entry contains the same columns the Afghan MoPH paper register requires: sequential number, date, patient reference, test type, result summary, technician ID, authorization status
2. **And** the logbook is searchable by date range, test type, patient reference, and technician
3. **And** it can be exported as a printable PDF matching the MoPH register format
4. **And** the logbook is stored in Dexie (offline-first) with sync to Hub
5. **And** logbook entries are append-only and cannot be edited or deleted

## Dev Notes

### Data Model — `LabLogbookEntry`

```typescript
export interface LabLogbookEntry {
  id: string                    // UUID v4 — primary key
  seqNo: number                 // Sequential register number (1, 2, 3...)
  facilityPrefix: string        // e.g., "KBL" — namespaces the seqNo for multi-facility
  displayNumber: string         // Computed: `${facilityPrefix}-${seqNo.toString().padStart(4, '0')}` e.g., "KBL-0001"
  date: string                  // ISO 8601 date of result authorization
  patientRef: string            // Opaque patient reference ID (NOT name — data minimization)
  patientFirstName: string      // First name only (CLAUDE.md Rule #7 — lab sees name + age only)
  patientAge: number            // Age at time of test
  testType: string              // LOINC display name (e.g., "Complete Blood Count")
  testLoincCode: string         // LOINC code (e.g., "58410-2")
  resultSummary: string         // Free-text summary of result (e.g., "WBC 8.2, RBC 4.5, Hgb 14.1")
  technicianId: string          // Practitioner ID of the tech who performed the test
  technicianName: string        // Display name of technician
  authorizerId: string          // Practitioner ID of the authorizer (supervisor)
  authorizerName: string        // Display name of authorizer
  authorizationStatus: 'authorized' | 'amended'
  authorizedAt: string          // ISO 8601 timestamp of authorization
  diagnosticReportId: string    // FK to the DiagnosticReport that generated this entry
  entryType: 'original' | 'amendment'
  amendmentOf?: string          // If entryType === 'amendment', the `id` of the original entry
  amendmentReason?: string      // Required if entryType === 'amendment'
  createdAt: string             // ISO 8601 — when this logbook entry was created
  syncStatus: 'pending' | 'synced' // Hub sync state
}
```

### Append-Only Enforcement

The logbook is a legal register. Entries must never be modified or deleted:

1. **No `updateLogbookEntry()` or `deleteLogbookEntry()` functions** are exported from `db.ts`
2. The only write operations are `appendLogbookEntry()` and `appendLogbookAmendment()`
3. Corrections are handled by creating a new amendment entry that references the original — the original stays intact
4. The UI has no edit or delete buttons on logbook entries
5. Sync from Hub only inserts, never updates existing entries
6. This is conceptually aligned with CLAUDE.md Tier 1 conflict resolution (append-only), though logbook entries are Tier 2 for sync priority since they are clinical data created after authorization (not safety-critical in the conflict sense)

### Amendment Flow

When a result needs correction after authorization:

1. Supervisor navigates to the logbook entry
2. Clicks "Create Amendment"
3. Enters corrected values + mandatory `amendmentReason`
4. System creates a **new** logbook entry with:
   - New `seqNo` (next in sequence)
   - `entryType: 'amendment'`
   - `amendmentOf: originalEntry.id`
   - `authorizationStatus: 'amended'`
   - The corrected `resultSummary` and any changed fields
5. Original entry is **not touched** — its `authorizationStatus` remains `'authorized'`
6. The logbook list UI shows the amendment indented below the original, or with a visual link
7. PDF export includes both entries in sequence order with amendment clearly marked

### Afghan MoPH Register Columns

The paper register used in Afghan laboratories has these columns. The digital logbook must match this layout for regulatory compliance and inspector familiarity:

| # | Column | Maps To |
|---|--------|---------|
| 1 | Serial No. | `displayNumber` (e.g., KBL-0001) |
| 2 | Date | `date` |
| 3 | Patient Name/Ref | `patientFirstName` + `patientRef` |
| 4 | Age | `patientAge` |
| 5 | Test Name | `testType` |
| 6 | Result | `resultSummary` |
| 7 | Technician | `technicianName` |
| 8 | Authorized By | `authorizerName` |
| 9 | Status | `authorizationStatus` |
| 10 | Remarks | `amendmentReason` (if amendment) or empty |

### PDF Export Implementation

Use **jsPDF + jspdf-autotable** for client-side PDF generation (works offline):

```typescript
import jsPDF from 'jspdf'
import autoTable from 'jspdf-autotable'

export async function exportLogbookPdf(
  entries: LabLogbookEntry[],
  filters: { dateFrom?: string; dateTo?: string; testType?: string; technicianId?: string },
  facilityName: string,
  locale: string,
): Promise<Blob> {
  const isRtl = ['ar', 'prs', 'ps'].includes(locale)
  const doc = new jsPDF({ orientation: 'landscape', putOnlyUsedFonts: true })

  // Header
  doc.text(facilityName, isRtl ? doc.internal.pageSize.width - 14 : 14, 15)
  doc.text('Laboratory Register', isRtl ? doc.internal.pageSize.width - 14 : 14, 22)
  // ... date range, export timestamp

  // Table
  autoTable(doc, {
    head: [['#', 'Date', 'Patient', 'Age', 'Test', 'Result', 'Technician', 'Authorized By', 'Status', 'Remarks']],
    body: entries.map(e => [
      e.displayNumber,
      new Date(e.date).toLocaleDateString(),
      `${e.patientFirstName} (${e.patientRef})`,
      e.patientAge,
      e.testType,
      e.resultSummary,
      e.technicianName,
      e.authorizerName,
      e.authorizationStatus,
      e.amendmentReason ?? '',
    ]),
    startY: 30,
  })

  // Footer on each page
  const pageCount = doc.getNumberOfPages()
  for (let i = 1; i <= pageCount; i++) {
    doc.setPage(i)
    doc.text(`Page ${i} of ${pageCount}`, 14, doc.internal.pageSize.height - 10)
    doc.text('Generated by Ultranos Lab Lite', doc.internal.pageSize.width - 80, doc.internal.pageSize.height - 10)
  }

  return doc.output('blob')
}
```

### Relationship to Upload History (Story 17.3)

These are **two distinct views** with different purposes:

| Aspect | Upload History (`/history`) | Lab Logbook (`/logbook`) |
|--------|---------------------------|-------------------------|
| **Purpose** | Track upload pipeline status | Legal register of authorized results |
| **Data source** | Dexie upload queue + Hub API reports | Dexie `labLogbook` table |
| **Entries created** | When tech queues a file upload | When supervisor authorizes a result |
| **Statuses** | pending, uploading, completed, expired, failed | authorized, amended |
| **Editability** | Items can be discarded or re-uploaded | Append-only, no edits or deletes |
| **Legal weight** | Operational tracking | Regulatory compliance document |
| **PDF export** | No | Yes (MoPH format) |

The upload history page remains for operational tracking. The logbook is the official register. A cross-link banner connects the two.

- **Data minimization:** Patient data in logbook follows CLAUDE.md Rule #7 — first name + age only, no diagnosis, no medication history

### PHI Safety Reminders

- Logbook `resultSummary` contains clinical data — never log its content (CLAUDE.md Rule #1)
- Audit events reference entries by `seqNo` and `id` only — never include `resultSummary`, `patientFirstName`, or `patientRef` in audit payloads
- PDF export is a PHI operation — emit audit event before generating
- Error messages from logbook operations must be generic ("Failed to create logbook entry") — never include entry content

### Sync Considerations

- Logbook entries sync to Hub at Tier 2 priority (clinical data)
- Each entry is enqueued to `syncQueue` with `resourceType: 'LabLogbookEntry'` immediately after local Dexie insert
- Hub sync uses timestamp-based merge — if the same `diagnosticReportId` entry exists on Hub with a newer timestamp, Hub version wins
- Sequential numbering may diverge between devices if multiple techs authorize results offline simultaneously — the Hub reconciles by assigning canonical sequence numbers on merge, and the local `seqNo` is updated on next sync pull
- The `displayNumber` is re-computed from the Hub-canonical `seqNo` after sync reconciliation
